# 원문 분석 초기 적체 해소와 운영

GPU BGE-M3는 검색용 임베딩이다. 여기서 말하는 정책 조건·혜택의 원문 분석은 기존 Codyssey LLM이 수행하며 해당 제공업체의 사용량/요금이 발생한다. 공급자 요율을 알 수 없으므로 원화·달러 비용을 임의로 계산하지 않는다.

## 최초 전체 분석

서버에서 게시된 카탈로그의 미분석 수·실패 수·누적 토큰을 확인한다. 이 명령은 LLM을 호출하지 않는다.

```sh
cd /home1/ncloud/iumon
sudo docker compose exec -T app python batch.py --analysis-status
```

초기 적체는 일일 100건 배치를 기다리지 말고 별도 전체 작업으로 처리한다. 아래 작업은 수집·상세 API·중복 병합을 실행하지 않으며 현재 게시된 정책 중 분석 캐시가 없는 것만 처리한다. 중단 후 같은 명령으로 재개하면 완료된 정책을 다시 호출하지 않는다.

```sh
sudo docker compose exec -T app python batch.py --backfill --workers 2
```

`--retry-failed`를 함께 주면 현재 미분석 정책의 당일/3회 실패 재시도 보류를 해제한다. 잘못된 키·할당량·지속적인 원문 검증 실패의 원인을 먼저 확인하고 사용한다. 실패한 정책을 성공한 것으로 채우거나 자격을 추측하지 않는다. 미완료가 남은 전체 작업은 종료 코드 2이다.

## 이후 운영

수집 → 새 카탈로그 구성 → 새·변경 정책 분석 → 게시 순서로 처리한다. 분석을 실행하는 배치에서는 새 카탈로그의 분석 완료율이 **95% 이상일 때만** 게시하고, 그 전에는 이전 카탈로그를 계속 제공한다. 한도 때문에 덜 처리됐으면 캐시에 진행 상황을 보존하고 다음 실행에서 이어서 분석한다. 게시 보류/실패는 한 시간 뒤 재시도한다. 초기 전체 분석을 먼저 완료하고 `BATCH_LLM_LIMIT=all`로 변경분을 처리하면 적체가 반복되는 것을 줄일 수 있다. 공급자 장애·대규모 변경 시에는 기존 자료가 계속 표시될 수 있으므로 수집일과 운영 로그를 확인한다.

`--stages collect,details,publish` 또는 `BATCH_LLM_LIMIT=0`처럼 명시적으로 LLM 분석을 끈 실행은 이 준비율 검사를 적용하지 않는다. 이 모드는 분석 사전 준비를 보장하지 않는다.

기존 일일 배치는 원문·분석 모델·프롬프트 fingerprint가 바뀐 정책과 아직 미분석인 정책만 처리한다. `BATCH_LLM_LIMIT`은 이후 갱신의 비용 상한으로 유지할 수 있다. `all`이면 전체, 환경 설정 `0`이면 예약 LLM 작업을 끈다. 이는 추천 요청의 실시간 보충 분석을 끄는 설정이 아니다.

실시간 요청은 캐시를 먼저 읽고 누락만 분석한다. 같은 fingerprint의 작업은 SQLite의 임대 잠금으로 프로세스 간 공유한다. 모델 호출은 잠금을 가진 한 작업만 수행하고 다른 요청은 저장된 결과를 기다려 사용한다. 작업이 종료되면 잠금을 해제하고 비정상 종료로 남은 잠금은 10분 뒤 만료된다. 다른 정책의 분석을 전역 잠금으로 막지 않는다.

추천 결과는 공급자 거절(권한/한도), 일시적 응답 불가, 검증 실패를 구분하는 안내를 표시한다. 공급자 오류 원문·키·요청 내용은 사용자에게 노출하지 않는다.

`--analysis-status`의 사용량은 이 변경 이후, 공급자가 `usage`를 반환한 원문 분석 응답만 집계한다(UTC 일자·모델·호출 수·입력/출력 토큰). 과거 호출·usage 없는 응답·실패한 HTTP 호출의 과금은 포함되지 않을 수 있으므로 청구서는 제공업체 콘솔에서 확인한다. 질문/생활 이야기/개인 프로필은 사용량 표에 저장하지 않는다.
